If given a file path, read that file as the conversation source instead of the current conversation.

## ChatGPT and other no-filesystem hosts

When running in ChatGPT, or another host that cannot write to the user's local filesystem, the
handoff is a **copy-ready text artifact**, not a file operation:

- Do not attempt to create `~/.jstack/handoffs/`, claim a file was saved, or offer to launch a local
  task.
- Generate the complete handoff as one Markdown code block. Precede it with the suggested filename
  `session-YYYY-MM-DD-<short-slug>.md`.
- Make the handoff self-contained. It may reference durable URLs or user-provided file names, but must
  not depend on a local path the next ChatGPT session cannot read.
- End the block with: `Paste this handoff into a new chat and ask: Continue from this handoff.`

All save-path and launch instructions below apply only when the host can actually write the stated
location. This section takes precedence when it cannot.

## Two axes decide everything

1. **What artifact?**
   - **Normal** — a handoff *document* the next session reads and continues. You'll be back at the
   keyboard (attended).
- **Goal** — an outcome-led **`/goal` prompt** for a fresh execution session. It can run
  autonomously when appropriate and persists across `/resume`.
2. **Who sets the objective?** You describe it (**directed**), or the agent infers it from this
   session (**agent-decides**).

| | agent-decides | directed |
|---|---|---|
| **Normal** | `recap` | `directive` |
| **Goal** | `goal` | `goal <objective>` |

## Parse the argument → mode

| Argument | Mode | Reference |
|----------|------|-----------|
| empty | **recap** (Normal / agent-decides) — re-orient a fresh session to continue this work (file-pointer handoff) | `references/recap.md` |
| starts with `directive` (or any descriptive text with no keyword) | **directive** (Normal / directed) | `references/directive.md` |
| starts with `goal` | **goal** — rest of the line is the objective (directed); empty rest = agent-decides | `references/goal.md` (contract) + `references/goal-mode-template.md` (prompt) |

**Goal requires the explicit `goal` keyword** — never create an execution goal from bare text. If
you're unsure whether the user wants Normal or Goal, ask one line:
*"Directive (you'll be at the keyboard) or goal (fresh execution task)?"*

Goal mode's `/goal` prompt is **generated by filling `references/goal-mode-template.md`**, not
hand-typed each session — the recurring preamble (no-memory warning, subagent/checker protocol,
compaction recovery) ships from the template; you only fill its slots (goal sentence, handoff path,
repo path, stop condition).

## Codex Desktop: start the fresh task now

The handoff file remains the durable state. In Codex Desktop, it can also be the launch artifact for
a fresh task, so the user does not need to copy-paste a resume prompt.

- Launch only when the user explicitly authorizes immediate execution in this turn: for example,
  "start the handoff now", "create the fresh task", or "run this goal now". For a spec/ticket
  execution goal, always ask: `Spawn a fresh execution task for <spec-or-ticket title> now?` and
  wait for confirmation. Do not infer launch authorization from the existence of a ready artifact.
- After saving, if `codex_app__create_thread` is available, create the task in the handoff's stated
  project and working environment. First use `codex_app__list_projects`; use the current project and
  a local environment unless the handoff requires isolated worktree changes.
- Before creating the task, apply the active global `AGENTS.md` model-routing policy and explicitly set
  the resulting `model` and `thinking` on the new task.
  Goal-mode execution defaults to the global orchestrator lane (Sol / medium) unless that policy routes
  the task differently; its new main agent then delegates to the appropriate worker lanes as needed.
- For recap/directive, the new task prompt is: `Read and execute this handoff: <absolute path>.`
  Add only the requested execution emphasis.
- For a **spec/ticket execution goal**, save the handoff and ask for confirmation to spawn its fresh
  execution task. Only after a yes, create it when the tool is available. Its initial prompt is the
  completed `/goal` prompt from the template, not a normal resume line. Other goal handoffs likewise
  require explicit immediate-start authorization.
- When a task is launched, return its task link/directive and the handoff path. When launch was not
  explicitly authorized, return the usual paste-ready prompt instead.
- A fresh task is not a replacement for the handoff file: it starts with no current-session memory
  and must read the handoff before acting.

## Shared rules (all modes)

- Save to `~/.jstack/handoffs/session-YYYY-MM-DD-<short-slug>.md` (append `-2`, `-3` if the path
  exists). Slug from the directive/goal, or the session topic in recap. The **goal** mode suffixes
  the slug with `-goal`.
- Treat `~/.jstack/handoffs/` as the canonical output location. Do not create extra convenience
  copies beside the user's project artifacts unless they explicitly ask for duplicate copies.
- **Every handoff document opens with a repo + working-directory block** — "Run from `<repo-path>`;
  all relative paths resolve against it." Cross-repo continuations (a fresh clone, a worktree, a
  different venture repo) break silently without this; state it even when it seems obvious from the
  current session.
- **Completeness pass before saving** — re-scan the conversation for anything not yet captured:
  every decision agreed this session (watch for "we decided", "we agreed", "let's go with"), every
  in-flight artifact path (files created or modified but not yet referenced), and every unresolved
  question. A handoff that skips one forces the next session to rediscover it the hard way.
- **Close-out pairing** — before writing the handoff, check whether this session produced durable
  knowledge (a decision, a fact, a synthesis) not yet saved to the second brain. If so, prompt the
  `/jstack-savetobrain` hop first — a handoff without a paired brain save loses that knowledge once
  the session ends. Don't block on it; just surface the prompt.
- After saving, when no Codex task was launched, return a paste-ready prompt for the next session,
  e.g. `Read and execute this handoff: <absolute path>`, plus any one-line execution emphasis the
  user requested. When a Codex task was launched under the immediate-start rule, return its task
  link/directive and the handoff path instead. Do not only describe the file location.
- Do not duplicate content already captured in other artifacts (PRDs, plans, ADRs, issues, commits,
  diffs). Reference them by path or URL instead.
- Redact any sensitive information (API keys, passwords, PII).
- If your setup has a canonical-state save skill, mention it so the user can run that too when canon
  changed.
- Include a **Suggested skills** section listing skills the next agent should load.
